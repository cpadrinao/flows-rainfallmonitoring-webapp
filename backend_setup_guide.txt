================================================================================
  PART 1: PYTHON BACKEND — IS IT THE RIGHT CHOICE?
================================================================================

YES — Python is a solid and recommended choice for this project. Here's why:

  - Excellent libraries for HTTP requests: `httpx`, `requests`
  - Native async support with `asyncio` / `FastAPI` for real-time capabilities
  - Strong Supabase Python SDK (`supabase-py`) support
  - Great for scheduled tasks: `APScheduler` or `cron` via `schedule` library
  - Lightweight deployment options: Render, Railway, Fly.io, or even a VPS
  - Easy JSON handling, datetime manipulation, and data validation

  RECOMMENDED FRAMEWORK: FastAPI
  - Handles API routes cleanly (REST endpoints your Next.js frontend can call)
  - Built-in async support
  - Auto-generates Swagger docs at /docs
  - Type-safe with Pydantic models
  - Fast enough for a barangay-scale monitoring system

  Alternatively, if you want simpler setup with less boilerplate, Flask works too.
  But FastAPI is more future-proof and developer-friendly.


================================================================================
  PART 2: PRE-SETUP CHECKLIST — THINGS TO DO BEFORE CODING
================================================================================

  [ ] 1. CREATE SUPABASE PROJECT
        - Go to: https://supabase.com
        - Create a new project (free tier is sufficient to start)
        - Choose a region close to Philippines (Singapore is ideal)
        - Note down:
            * Project URL     (e.g., https://xxxx.supabase.co)
            * Anon Public Key (for frontend reads)
            * Service Role Key (for backend writes — KEEP THIS PRIVATE)

  [ ] 2. SETUP PYTHON ENVIRONMENT
        - Install Python 3.11+ from https://python.org
        - Create a virtual environment:
            python -m venv venv
            venv\Scripts\activate  (Windows)
        - Install required packages:
            pip install fastapi uvicorn supabase httpx python-dotenv apscheduler pydantic

  [ ] 3. CREATE .env FILE FOR SECRETS
        - Never hardcode credentials. Create a `.env` file:
            SUPABASE_URL=https://xxxx.supabase.co
            SUPABASE_SERVICE_KEY=your_service_role_key_here
            OPEN_METEO_LAT=14.0860   (Barangay Rizal, approximate coords)
            OPEN_METEO_LON=121.1000
            TIMEZONE=Asia/Manila
            FETCH_INTERVAL_MINUTES=60

  [ ] 4. ADD .env TO .gitignore
        - Prevent accidental secrets leak:
            echo ".env" >> .gitignore
            echo "venv/" >> .gitignore

  [ ] 5. SETUP SUPABASE ROW LEVEL SECURITY (RLS)
        - Enable RLS on all tables in Supabase Dashboard
        - Set policies (explained in Part 3)

  [ ] 6. SETUP SUPABASE API KEYS POLICY
        - Anon Key: Allow SELECT (read) on public-facing tables
        - Service Role Key: Allow INSERT/UPDATE/DELETE (backend only)

  [ ] 7. INSTALL SUPABASE CLI (OPTIONAL BUT RECOMMENDED)
        - For local development and schema migrations:
            npm install -g supabase
            supabase login
            supabase init
            supabase db push

  [ ] 8. DECIDE HOSTING STRATEGY
        - Backend (Python FastAPI): Deploy to Railway / Render / Fly.io
        - Frontend (Next.js): Already on Vercel or similar
        - Cron Job: Use APScheduler inside FastAPI OR use Supabase's built-in
          Edge Functions if you prefer serverless


================================================================================
  PART 3: SUPABASE DATABASE TABLES
================================================================================

  Below are the recommended tables for F.L.O.W.S. to work end-to-end.
  All tables should have RLS enabled.

  ─────────────────────────────────────────────────────────────────────────────
  TABLE 1: zones
  Purpose: Stores each monitoring zone in Barangay Rizal
  ─────────────────────────────────────────────────────────────────────────────

  Column Name        Data Type       Notes
  ─────────────────  ─────────────  ─────────────────────────────────────────
  id                 uuid            PRIMARY KEY, default: gen_random_uuid()
  name               text            NOT NULL, e.g., "Zone 1 - Riverside"
  latitude           numeric(10,6)   Precise GPS latitude of the zone
  longitude          numeric(10,6)   Precise GPS longitude of the zone
  description        text            Optional description of the zone area
  is_active          boolean         Default: true. Soft-delete support
  alert_level        text            Values: 'Green', 'Yellow', 'Orange', 'Red'
  created_at         timestamptz     Default: now()
  updated_at         timestamptz     Auto-updated via trigger

  RLS Policy:
  - Public (anon): SELECT is_active = true zones only
  - Backend (service role): Full CRUD

  ─────────────────────────────────────────────────────────────────────────────
  TABLE 2: weather_logs
  Purpose: Stores every hourly forecast record fetched from Open-Meteo
  ─────────────────────────────────────────────────────────────────────────────

  Column Name             Data Type       Notes
  ─────────────────────  ─────────────  ──────────────────────────────────────
  id                     uuid            PRIMARY KEY, default: gen_random_uuid()
  zone_id                uuid            FOREIGN KEY -> zones(id)
  fetched_at             timestamptz     When the fetch occurred (Philippine Time)
  forecast_time          timestamptz     The hourly forecast timestamp from API
  precipitation_mm       numeric(8,2)    Rainfall amount in mm (precipitation)
  precipitation_prob     int             0–100% chance of precipitation
  temperature_c          numeric(5,2)    Temperature in Celsius
  relative_humidity      int             0–100% relative humidity
  wind_speed_kmh         numeric(6,2)    Wind speed at 10m height, km/h
  wind_direction_deg     int             Wind direction in degrees
  weather_code           int             WMO weather code (e.g. 61=rain, 95=storm)
  cloud_cover_pct        int             Total cloud cover 0–100%
  visibility_m           numeric(10,1)   Visibility in meters
  validation_status      text            Values: 'PASSED', 'FLAGGED', 'CORRECTED'
  validation_notes       text            Optional notes from admin review
  created_at             timestamptz     Default: now()

  RLS Policy:
  - Public (anon): SELECT all (residents can read logs)
  - Backend (service role): INSERT/UPDATE
  - Admin: UPDATE validation_status and validation_notes only

  ─────────────────────────────────────────────────────────────────────────────
  TABLE 3: alert_events
  Purpose: Logs when alert levels change or thresholds are crossed
  ─────────────────────────────────────────────────────────────────────────────

  Column Name        Data Type       Notes
  ─────────────────  ─────────────  ─────────────────────────────────────────
  id                 uuid            PRIMARY KEY, default: gen_random_uuid()
  zone_id            uuid            FOREIGN KEY -> zones(id)
  alert_level        text            'Green', 'Yellow', 'Orange', 'Red'
  trigger_value      numeric(8,2)    The rainfall mm value that triggered it
  message            text            Auto-generated advisory message
  is_active          boolean         True = still ongoing alert
  triggered_at       timestamptz     When the threshold was crossed
  resolved_at        timestamptz     When it was cleared (nullable)
  created_at         timestamptz     Default: now()

  RLS Policy:
  - Public (anon): SELECT is_active = true events
  - Backend (service role): Full CRUD

  ─────────────────────────────────────────────────────────────────────────────
  TABLE 4: admin_users
  Purpose: Admin account management (separate from Supabase Auth if needed)
  ─────────────────────────────────────────────────────────────────────────────

  RECOMMENDATION: Use Supabase built-in Auth instead of a custom table.
  This is safer and handles password hashing automatically.

  If using Supabase Auth:
  - Enable Email/Password auth in Supabase Dashboard > Authentication
  - Create admin users via the Supabase dashboard directly
  - Use Supabase JWT tokens on the frontend to verify admin sessions

  If you still want a custom table (for role tracking):

  Column Name        Data Type       Notes
  ─────────────────  ─────────────  ─────────────────────────────────────────
  id                 uuid            PRIMARY KEY, links to auth.users(id)
  username           text            Display name
  role               text            'admin' or 'superadmin'
  last_login         timestamptz     Track last login time
  created_at         timestamptz     Default: now()

  RLS Policy:
  - Only service role can read/write this table
  - Never expose to anon key

  ─────────────────────────────────────────────────────────────────────────────
  TABLE 5: system_config
  Purpose: Store system-level settings (fetch intervals, thresholds, etc.)
  ─────────────────────────────────────────────────────────────────────────────

  Column Name           Data Type       Notes
  ───────────────────  ─────────────  ───────────────────────────────────────
  id                   int             PRIMARY KEY (simple integer)
  fetch_interval_min   int             Default: 60 (how often to call API)
  rain_yellow_mm       numeric(5,2)    Threshold for Yellow alert (e.g. 7.5)
  rain_orange_mm       numeric(5,2)    Threshold for Orange alert (e.g. 15.0)
  rain_red_mm          numeric(5,2)    Threshold for Red alert (e.g. 30.0)
  last_fetch_time      timestamptz     When the API was last successfully called
  system_status        text            'online', 'degraded', 'offline'
  updated_at           timestamptz     Auto-updated via trigger

  RLS Policy:
  - Public (anon): SELECT system_status and last_fetch_time only
  - Backend (service role): Full UPDATE access


================================================================================
  PART 4: SUPABASE SECURITY MEASURES
================================================================================

  1. ROW LEVEL SECURITY (RLS)
     - Enable RLS on EVERY table without exception
     - Default behavior with RLS enabled = deny all (safe default)
     - Only grant access through explicit policies

  2. API KEY MANAGEMENT
     - Anon Key: Use in Next.js frontend (safe for public read)
     - Service Role Key: Use ONLY in Python backend via .env file
     - NEVER expose Service Role Key in frontend code or git commits

  3. SUPABASE VAULT / SECRETS
     - Store sensitive values in Supabase Vault (Dashboard > Vault)
     - Can store Open-Meteo coordinates, alert thresholds securely

  4. HTTPS ONLY
     - Supabase enforces HTTPS by default — no action needed
     - Ensure your FastAPI backend is also deployed behind HTTPS

  5. CORS POLICY
     - In FastAPI, restrict CORS to only your frontend domain:
         origins = ["https://your-flows-app.vercel.app"]
     - Don't use wildcard (*) in production

  6. RATE LIMITING (OPTIONAL BUT RECOMMENDED)
     - Add slowapi or similar to FastAPI to prevent API abuse
     - Open-Meteo is free but has rate limits: respect them

  7. ENVIRONMENT VARIABLE VALIDATION
     - Use Pydantic Settings to validate all env vars on startup
     - Fail fast if any required env var is missing

  8. SUPABASE AUTH FOR ADMIN PORTAL
     - Use Supabase's built-in Auth for admin login
     - Verify JWT tokens on the Next.js side using @supabase/ssr
     - Protect /admin/* routes with middleware checks

  9. AUDIT LOGGING
     - The weather_logs table serves as an audit trail
     - Never allow DELETE on weather_logs — only INSERT and UPDATE
     - Consider a Supabase trigger to log any admin changes to a separate
       audit_log table

  10. DATABASE BACKUPS
      - Supabase Pro tier includes automatic daily backups
      - Free tier: manually export using pg_dump if critical
      - Consider scheduling a weekly export script in Python


================================================================================
  PART 5: OPEN-METEO API — HOURLY VARIABLES GUIDE
================================================================================

  Open-Meteo is FREE, no API key required for reasonable use.
  Base Endpoint: https://api.open-meteo.com/v1/forecast

  COORDINATES FOR BARANGAY RIZAL (approximate — verify exact location):
  Latitude:  14.0860
  Longitude: 121.1000

  Always set: timezone=Asia%2FManila (URL encoded) so timestamps are in PHT

  ─────────────────────────────────────────────────────────────────────────────
  RECOMMENDED HOURLY VARIABLES TO INCLUDE:
  ─────────────────────────────────────────────────────────────────────────────

  MUST HAVE (Core Rainfall Monitoring):
  ✓ precipitation           — Actual total precipitation in mm (rain + snow)
                              This is the PRIMARY metric for your alerts
  ✓ precipitation_probability — Percentage chance of rain (0–100%)
                              Useful for advance warnings

  SHOULD HAVE (Contextual Weather Data):
  ✓ relative_humidity_2m    — Humidity at 2 meters, in %
                              Shows moisture conditions
  ✓ temperature_2m          — Air temperature in Celsius
                              General weather context
  ✓ weather_code            — WMO code describing conditions
                              61/63/65 = light/mod/heavy rain
                              80/81/82 = rain showers
                              95 = thunderstorm
                              Useful for setting alert messages
  ✓ cloud_cover             — Total cloud cover in %
                              Helps predict upcoming rain
  ✓ wind_speed_10m          — Wind speed in km/h
                              Useful during typhoon monitoring
  ✓ wind_direction_10m      — Wind direction in degrees
                              Shows wind patterns

  NICE TO HAVE (Extended Monitoring):
  ~ visibility              — Visibility in meters
                              Low visibility = severe weather indicator
  ~ surface_pressure        — Atmospheric pressure in hPa
                              Dropping pressure = incoming storm
  ~ et0_fao_evapotranspiration — Soil moisture proxy
                              Relevant if monitoring landslide risk

  SKIP FOR NOW (Not relevant for rainfall monitoring):
  ✗ shortwave_radiation      — Solar data, not needed
  ✗ direct_radiation         — Same, not needed
  ✗ uv_index                 — UV monitoring, out of scope
  ✗ cape                     — Convective energy, too advanced for now

  ─────────────────────────────────────────────────────────────────────────────
  SAMPLE OPEN-METEO API CALL (Copy-paste ready):
  ─────────────────────────────────────────────────────────────────────────────

  https://api.open-meteo.com/v1/forecast
    ?latitude=14.0860
    &longitude=121.1000
    &hourly=precipitation,precipitation_probability,temperature_2m,
            relative_humidity_2m,weather_code,cloud_cover,
            wind_speed_10m,wind_direction_10m,visibility
    &timezone=Asia%2FManila
    &forecast_days=1

  (Combine all hourly params as comma-separated values in one &hourly= param)

  ─────────────────────────────────────────────────────────────────────────────
  WMO WEATHER CODE REFERENCE (For Alert Logic):
  ─────────────────────────────────────────────────────────────────────────────

  Code  Description
  ────  ─────────────────────────────
  0     Clear sky
  1-3   Mainly clear / partly cloudy
  45-48 Fog
  51-55 Drizzle (light to dense)
  61    Slight rain
  63    Moderate rain               ← Yellow alert trigger candidate
  65    Heavy rain                  ← Orange alert trigger candidate
  80    Slight rain showers
  81    Moderate rain showers       ← Orange alert trigger candidate
  82    Violent rain showers        ← Red alert trigger candidate
  95    Thunderstorm                ← Red alert trigger candidate
  96-99 Thunderstorm with hail      ← Red alert, immediate warning


================================================================================
  PART 6: RECOMMENDED ALERT THRESHOLD LOGIC
================================================================================

  Base thresholds on PAGASA rainfall intensity guidelines:

  Alert Level   Rainfall per Hour   Action
  ───────────   ─────────────────   ─────────────────────────────────────────
  GREEN         0 – 7.4 mm          Normal monitoring, no action needed
  YELLOW        7.5 – 14.9 mm       Monitor closely, prepare residents
  ORANGE        15.0 – 29.9 mm      Activate evacuation standby
  RED           30.0 mm and above   Immediate evacuation warning

  Implement this logic in your Python backend:
  - After each API fetch, compare precipitation value to thresholds
  - Update zone alert_level in Supabase
  - Insert into alert_events table if level changed
  - Generate advisory message text automatically
